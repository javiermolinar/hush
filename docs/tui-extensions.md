# Go TUI extension API

The public package is `github.com/javiermolinar/hush/tui/extension`. Its first source API is **0.1.0**. While it is 0.x, a host accepts registrations authored against the same major and minor; patches are compatible. Authors declare the version they target, not a version dynamically inferred from the running host. A breaking pre-1.0 change requires a new minor. From 1.0 onward, use SemVer: no breaking changes within a major, and a host must be at least as new as the minor an extension targets. These rules are separate from Go module releases and native protocol version negotiation. Every extension is recompiled with the host.

[ADR 0002](adr/0002-extension-loading.md) chooses explicit linked registration. A custom build imports the extension packages, calls their constructors, and passes their `extension.Registration` values to the shell. The [inbox example](../tui/examples/inbox/inbox.go) is a separate Go package; a build would include `inbox.New()` in its registration list. No `init`-time registration, source discovery, plugins, or runtime reloading. Linked code has full process privileges: use trusted code only. An eventual remote loader could transport declarative snapshots, content, and action requests and cache their contributions asynchronously. The Go API, function values, and Bubble Tea models are not that wire protocol.

## What library users can extend

A linked package can register its own actions, dialogs, status segments, widgets and renderers. For instance, build a thread switcher with `ListThreads`, `SelectDialog` and `Switch`, a fork picker with `History` and `Fork`, or a model/thinking picker with `ListModels` and `ConfigureCatalog` or `Configure`, depending on the catalog. Use distinct action IDs, slash names and bindings: registration adds contributions; it does not replace the shell's built-ins.

The shell owns integrated `@` file search and completion, Git diff review, native skill discovery and insertion, workspace trust UI, images, and the intro. An embedding app uses the built-in UI where its `tui.Options` and host support it. An extension can build a separate listing with `ListFiles` or `ListSkills` on supported hosts, but it cannot take over the built-in picker, watches, or editor routing through those operations. See the [built-in boundary](adr/0002-extension-loading.md#built-in-boundary).

## Run a linked build

[`tui/examples/attach`](../tui/examples/attach/main.go) registers the sample
extension with `tui.New` and `Model.Run`. The native SDK backs the thread list,
history, fork and configuration. The shell probes the native model catalog
for available models and thinking levels.
The reference backend negotiates optional title changes through intro v2, and
worktree creation (`NewWorktree`) and archive visibility through thread directory v2.
`tui.MenuServices` can supply alternate title/archive and file adapters or add
permission-mode controls. The reference backend can offer workspace browsing and
search through negotiated `workspaceFiles`, subject to workspace grants. The
attach example does not request that capability. A custom `MenuServices.Files`
adapter returns workspace-relative children of the requested directory, with
optional page cursors, and enforces its own authorization. It does not enable
native search. The shell applies completion only to the active request and editor
token.

`Options.ProviderLogin` lets a managed local frontend supply `/login` with a
fixed list of providers and a trusted terminal command for each. The linked
attach example leaves it unset. Sign-in does not pass credentials to the shell
model, extensions, or the SDK.

`Options.ProjectThread` optionally supplies authoritative chrome metadata. The
shell does not use cumulative usage as context occupancy or label transcript
entries as file snapshots unless the host identifies them explicitly.

## Registry and lifecycle

- The same registry validates and dispatches shell and external registrations. Some shell actions call private handlers. External actions use only the public contexts, continuations and effects described here. The shell owns focus, layout, default renderers, frontend state and SDK transport. A footer is composed from `Segment`s over `Context.Thread` and host-managed status contributions, not a privately supplied model or footer interface. In the attach client, sheets sit above the fixed status line.
- Validate the complete registry before running `Init`. Duplicate extension IDs, fully qualified action IDs, globally visible slash names, exact entry renderer kinds or exact tool renderer names are errors. Contribution keys are local to the extension and unique within their contribution family (segments, widgets, summarizers); qualify them with the extension ID for ordering. `SetStatus` keys are separate, scoped to extension and owning thread; they replace their previous value, contribute to the status line, and are cleared at owner teardown. Subscriptions to the same event are multicast in registration and declaration order. Renderer registration is not a chain of overrides: a hook can decline and use the default. Invalid declarations are errors even if currently capability-gated.
- The host normalizes shortcuts, reserves shell/editor keys needed for safe input and focus, and rejects duplicate direct chords or leader sequences, including prefix conflicts in leader sequences; it applies the same checks to any user remapping. No silent replacement by load order. A palette row and a leader-strip entry reference the same action and display the effective binding, including the leader alternative when a terminal is known to intercept the direct chord. Use `Requires` and `Available` on both surfaces and recheck them on dispatch. A slash alias, direct chord or clickable span does not install a second handler or bypass availability.
- `Init` runs in registration order once per successful shell startup attempt, not on every tab switch. Admit its effects after all instances initialize successfully. On init failure, discard pending effects, clean up the instances whose init already succeeded (in reverse order), and report startup failure. On ordinary teardown, stop dispatch, cancel owned work, invalidate pending completion/dialog routing, and call `Shutdown` in reverse order. Neither lifecycle callback may block. No callbacks after shutdown; a request canceled locally may have already reached the server.
- Treat all inputs as immutable. The host detaches slice, pointer and byte data in SDK projections before handing them to callbacks; they never alias the SDK replica or another callback's editable data. Value snapshots can be retained, but are not live. Callbacks relinquish ownership of returned slices and result data. IDs are opaque and stable within their source domain; an inherited entry's recorded origin is distinct from the viewing thread. The host scopes IDs to its data store; a reconnect is not itself a new store or a replayable log.

## Loop, ownership, and dialogs

All callbacks on the loop, including actions, continuations, lifecycle, summarizers, completion and observers, must be bounded and nonblocking. Observers are post-commit and cannot emit effects, veto transitions or edit entries; they can hold bounded instance-local data for later actions. A completion returns an item and a UTF-8 byte-range edit in the current argument tail, not an input submission. Use only supplied data or immutable precomputed tables in completion; no synchronous IO or waiting. The host validates range boundaries, caps items, and rejects stale edits.

An action returns immediate `Outcome` values, not a private model mutation. The shell admits effects in order and interprets them in its update loop; that does not sequence async completions. Use continuations for dependent steps, for example `Fork` → `Switch{ThreadID: result.ThreadID}`. `Client` is the SDK facade: the shell validates it, starts SDK calls off the loop and delivers the projected reply to `Done` on the loop. Missing optional support (including support lost since display) returns `ErrUnavailable` and does no operation. `Submit`/`Steer` return a submission ID for admission, not settlement; `Compact` returns an admitted task ID; new, fork and switch return the resulting thread ID. Listings populate only their matching slice and optional cursor. The SDK retains responsibility for submission key/retry semantics and indeterminate transport errors; do not automatically retry unkeyed mutations. `Work` is for extension-local async computation or IO, with a host-owned cancellation context and one result returned to `Done` on the loop. A worker never reads or writes loop-owned state. Immediate effects such as notices and status also go through the loop; they never write to stdout. With no result handler the shell can report diagnostics using its own notice policy.

At dispatch, capture the registration instance, original owning thread (which may be empty or inactive), and store scope; give each pending request/dialog its own routing token. A continuation receives a **fresh snapshot of that owner**, not a snapshot of whichever tab is active when the reply arrives. Changing the active tab does not rebind a continuation or a zero target. An unbound continuation must name a target for any thread-scoped operation. Explicit target IDs act on that target but do not change the continuation owner. Hit targets inherit the owning thread of the surface they were drawn on. Drop late results after shutdown, owner removal or store replacement; cancel work where possible. Discard stale input/clicks rather than retarget them. Success, error and dismissal are each delivered at most once for a live request; remove a finished dialog before running its continuation. For dispatch chains the shell enforces an effect/depth budget.

- **Sheet** is a single docked form or filtered list. At most one sheet is visible; a replacement dismisses the previous sheet. A sheet can reference existing actions and pass the highlighted choice's stable ID to them. Those actions can open a dialog above the sheet without first closing it.
- **Overlay** pushes onto the shell's dialog stack. The focused panel docks to the input rule above the prompt. It can sit above the command palette or above a sheet. Every key and click goes first and only to the top overlay when there is one; Escape closes that overlay only, does not reach the child model, and does not seed the shell's double-Escape behavior. An outside click, where used for dismissal, does not click through. When no overlay remains, the preserved sheet or underlying focus resumes. Select returns a choice ID; the optional choice `Action` is a presentation-only verb for the consequence line; explicit No and accepted empty text are distinct from dismissal.
- **CustomDialog** is host-gated and uses the same dock. Instantiate a fresh pinned Bubble Tea v2 `tea.Model`; the shell calls `Init`, feeds layout size and focused input through `Update`, keeps the returned model, and takes only the textual content of `View`. Check `Result` after init/update and close that instance on completion. The shell runs ordinary commands (for example a `tea.Tick` returning a dialog message) away from the loop, scopes each result to that dialog token, and drops it when the dialog closes. Covered dialogs may receive their own command or layout messages, but never keys or clicks. Returned messages are not resent to the parent as program controls. Global commands, program options and terminal modes are not part of this contract; do not depend on the parent processing nested program-control, batch or sequence messages. No nested Tea programs, raw terminal writes, or direct input subscriptions. Use `Work` for independently cancelable IO.

## Rendering and source limits

Native Go hooks can implement custom layout logic in-process, but return semantic blocks/spans or delegate Markdown/code/diff layout to the host. Multiple logical lines can wrap; the shell alone measures cells, caps bytes/rows, and derives targets from the actual drawn spans. Content, labels, notices, diagnostics, and delegated document text are untrusted display strings. The shell normalizes text, visualizes unsafe control characters, validates links against the workspace and URL policy, and generates escapes only after validation. Custom Tea content can preserve validated styling SGR within each row only; arbitrary escape sequences, clipboard writes, hyperlinks and terminal-mode changes in a view must not pass through. A tool hook receives a one-row budget in the live activity slot; if the hook declines, the shell keeps its default status and output preview. The host may enforce smaller bounds when space is scarce. Theme values and semantic roles let the shell apply the terminal's palette and fills policy instead of accepting hard-coded styles. Lazy rendering and caching should depend on render inputs, including owner and revision, width, palette revision, tool-expanded, reasoning-expanded and live state, style settings and row budget. `RenderContext.Expanded` controls tool details; `ReasoningExpanded` independently controls supplied reasoning. Summarizers receive a bounded sample of committed tool results, not a whole transcript, and can add a note without changing the group or its counts. Segment priority controls which chrome survives; order controls its position, independently of priority.

Use SDK value types where they already express native semantics: durable IDs, model references, usage, entry/generation projections and tri-state configuration. The client facade does not hand out the SDK client, SDK watch channels, or full mutable replica. `Watch` publishes latest snapshots and may coalesce transitions or reconnect onto a new snapshot. `EntryObserved` is an observation of a newly incorporated record (including catch-up), not a live-only append notification; deduplicate overlap by viewing thread and entry ID. Stream and retained tool output are snapshots, not deltas. A short call may produce a result without its start or output being seen. Usage is reported totals, not a model catalog or context estimate. `Thread.Usage` is the thread's own usage, as in core state; `Thread.SubagentUsage` is its subagents' usage in addition to that, followed only for the active thread and zero otherwise. Add the two for the thread's spend. `UsageChanged` fires when either changes. The [native core](../protocol/v1/README.md) supplies no provider payloads, raw custom entry data, redacted thinking, image bytes, or approval feed. Don't invent those or treat disappearance from a live slot as success. Files, archive, permission mode, titles and approvals are host-gated, not guaranteed by native v1. Clients can supply a custom catalog with `tui.MenuServices`.
