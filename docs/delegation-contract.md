# Independent review delegation: backend contract

This describes the backend boundary for [native code review delegation](../protocol/v1/delegation.md). It supersedes the automatic delegation and follow-up design in Hyperion's `plans/02-agent-execution.md` r2 and consolidates Hush's saved **Tooling and delegation: independent reviews and joins** r3 and the `04-subagents` draft. Hush already stores typed plan revisions in Durable. `/plan` browses; Space selects; Enter admits selected tasks in the current checkout; `w` prepares a separate checkout from committed HEAD with the selected model and corresponding subdirectory, subject to that checkout's trust; `s` opts into scoped verification. Keep those paths. Do not import a plan runner, file-backed plan store, scheduler, or transcript store from another project.

The [contract fixture](../backend/test/delegation-contract.test.mjs) uses only public APIs, a scripted provider and disposable SQLite. It launches one synthetic child, observes the parent join and child park, checks `wake()` has no runnable work or deadline and the provider has zero open requests, and runs a separate probe completion. It kills the parked process, reopens it, releases the child, observes the display-only notice on the already attached parent view and kills the process again after the outcome commit but before the join result commits. The next boot completes the same parent submission and first entry, with one notice, two tool results (spawn and join), one child input and one parent synthesis. A further boot sends no model request. There is no periodic check or open request while the parent parks. This proves the commit boundaries, not live model behavior, mixed cohorts, cancellation races, full admission, or socket projection. Run `node --test backend/test/delegation-contract.test.mjs`.

## Ownership and commits

- **Explicit admission.** The initiating parent and run, store identity, request/cohort key, assignment ID, exact model and thinking, brief, execution mode, snapshot and canonical scope belong in the receipt. Same key and payload return the same receipt; same key and different payload conflict. Check the two-unsettled limit across peers and turns in the reservation commit; unresolved reservations still hold capacity. Omitted mode is sequential. Model spawn is valid only inside the exact native run explicitly authorized to delegate. Preparing a draft or staged model, browsing a snapshot, marking tasks, attaching a peer, and reading a notice never grant launch or join authority. Never turn plan drafting, plan runs, review workers, headless auto-delegation, private invocations or Pi RPC into delegation entry points.
- **Create and submit.** Commit intent with the worker task; in a task commit record the child ownership edge, cleared inherited loadout, profile and child ID together. A child has its own conversation and provider session, not fork history. Put the one keyed child submission and the coordinator's `SubmissionSettled` sleep/checkpoint in a single commit. A lost reply reopens those same identities. Do not use a terminal-looking slot, process-local map or assistant prose as evidence that a child ran or settled. A missing or contradictory identity is unresolved, not permission to recreate it. A live coordinator's phase, child and submission checkpoint must agree with the receipt before its evidence is usable, including during timeout, Stop and restart recovery. A held reservation cannot advance past the gate phase. Spawn correlates every held assignment before releasing the cohort; it does not start a worker whose Stop outcome is already committed.
- **Park and settle.** For a join, check every handle under the exact parent scope and record the join task/key for each unsettled outcome. If the outcome raced this registration, the same transaction can already read it. A signal delivered before the tool actually sleeps is retained. A coordinator observes the committed child submission and reads its bounded report or failure; it commits the receipt, one attributed parent `appendEntry` with no `model`, and applicable `Tx.signal()` calls together. Perform signal calls before the first table write; a closed or expired join does not prevent committing the outcome. Signals carry outcome identities, not report bodies. Keys are single-use: for a multi-worker join, wait on still-pending keys or use a fresh key after a wake; reread all owned receipts rather than using a signal as authority. A committed result is stable if Stop arrives later; an acknowledged abort is not terminal evidence. An expired join wait is not a timed-out worker. Do not free the slot for a missing or unknown outcome.
- **Resume or inspect.** Late/repeated joins read existing receipts without running other work. A terminal notice does not make an unreleased reservation joinable. Each join returns separately attributed results, retaining the successful siblings of a failed or unresolved worker. Join waits only on correlatable pending workers and reports unresolved evidence separately from settlement. Durable commits the join tool result separately and resumes its original generation. If nobody joins, post only the notice, with no input, steering, follow-up, polling or wake-up generation. Projection watches the parent; opening a pane or child transcript is explicit and unnecessary for settlement. A report is advisory, never permission to fix, verify, select, merge or approve.

## Compatibility

`delegation:1` gates launch, inspection, Stop, and parent notices. Core projection and history use the same visibility rule and preserve visible anchors across reconnect; inherited notices remain on the original parent. `reviewEvidence:1` adds pinned acceptance checks and labeled supplied excerpts at launch. `workerActivity:1` adds a separate roster and explicit parent-scoped dossier and public transcript reads. Roster changes are wakeups from Durable publications, not new scheduled work or a transcript store. Old clients keep their original operations. Ordinary native thread reads hide task-owned code reviewers even when the assigned tool policy is unavailable. Established plan-owned transcripts remain readable. `/plan` review uses its own capability and keeps its existing target and restart behavior. Unnegotiated, private, and Pi clients don't gain launch or notices.

## Execution and evidence

The backend saves the effective turn policy; a native run follows its first input identity (or explicit Continue submission), and a task-owned run uses an immutable owner-bound profile. Existing scoped plan turns use their committed reservation and file proposals. Planner intent comes only from placed inputs: it can narrow a running turn but preview cannot become save by steering. Continuing or forking an inherited restricted transcript does not mint authority. A fresh authorized request can start a new run. Policy checks run inside the tool execution entry point, including nested calls and replay after Durable's execute-intent checkpoint. Provider tool lists are presentation. Default retains the configured coding tools and normal `LocalEnvironment`; trust and cwd are not a shell or filesystem sandbox. Read-only and worker live reads use bounded workspace-relative UTF-8 paths with no links; a scoped worker adds an exact file allowlist. Codemode journals can replay a stored inner result only under the unchanged outer grant. A revoked and recreated grant is a different grant. Plan proposals still check the revision and are not file writes. No private tools or parked approvals are enabled by this change.

Plan review is a separate target kind: pinned plan revision and captured requirements, no file tools, final structured report only. Code review pins an explicitly supplied set of tracked paths (including context) and untracked paths below the thread's exact authorized cwd. The backend captures bounded UTF-8 base, staged and working versions, preserving modes and bytes, including missing versions for additions/deletions. That is a lossless representation of both diffs for the admitted paths, not `git diff HEAD`, which would collapse staged and unstaged changes. It does not copy history, Git configuration, ignored/unadmitted files, or credentials. Unsupported modes, conflicts, intent-to-add index entries (`git add -N`), ambiguous or drifting names, ignored inputs, and oversized or unavailable content fail closed rather than skipping files. Stage an intent-to-add path before including it in the tracked review scope. Legitimate tracked content is still the operator's responsibility to scope. The content-addressed manifest and bytes are stored in the same Durable store; reviewers can read only the assigned versions, never fall back to the worktree. A separate freshness observation rechecks target identity, scope, and content without mutating the captured input or implying that the filesystem is locked. The launch receipt and each worker's replay fence bind the snapshot, canonical read claims and exact selection. `status` compares the sealed target to a new observation; only the sealed target enters the reviewer. The reviewer records a bounded advisory report through its own tool. The report can distinguish source lines actually read, caller-supplied test excerpts not rerun, and missing evidence. A child submission must settle before that report becomes a terminal outcome. No checkout, trust grant or merge is created by snapshot capture.

The coordinator uses `abandonOnRestart`; Durable marks it and drains its owned generation before running recovery. Recovery may collect an already committed child settlement, but it cannot restart a child submitted or reserved before the process loss. If the original child, submission, task, or outcome cannot be matched, the slot remains unresolved. No component polls or generates follow-up prompts. A join seeing an unexpected task fault without a settlement commit may wait until its own deadline; `status` can show the unresolved receipt earlier. The production restart fixture uses loopback providers and disposable SQLite at the snapshot, admission, child-open, child-submit, provider-in-flight, child-settlement, notice, and join-result boundaries.

## Local regression fixtures

- [`app/test/review.test.mjs`](../app/test/review.test.mjs) uses one explicit CLI admission and an 80×24 Hush PTY. Both workers read the same base, index, and dirty bytes; the operator inspects supplied evidence and reattaches while the same parent join is parked. The original submission synthesizes one report and one worker timeout. The fixture checks that tracked diffs and the untracked file inventory are unchanged, there is one notice per worker, and actual Codemode dispatch reads a file but cannot spawn or join.
- [`backend/test/review-delegation.test.mjs`](../backend/test/review-delegation.test.mjs) covers two peers, exact and lost replies, restart boundaries, unresolved evidence, late Stop, and independent read/check citations. The ordinary [unsafe-tool crash fixture](../backend/test/backend.test.mjs) checks a running replay-unsafe tool separately.
- [`app/test/plan.test.mjs`](../app/test/plan.test.mjs) still drives `/plan` at startup, on a foreign workspace and at a historical fork pin, and exercises Enter, `w`, `s`, and plan review independently of delegation. [`backend/test/plan-worktree.test.mjs`](../backend/test/plan-worktree.test.mjs) checks the staged model and subdirectory, exact trust, lost replies, and history on the source plan.

These are scripted checks against disposable stores. They do not cover provider behavior in production, OS notifications, or opening a live Rex pane.
