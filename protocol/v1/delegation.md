# Native code review delegation (`delegation:1`)

A persistent, writable Hush backend can negotiate `delegation:1` in `hello`. No operation is inferred from the model, a prompt in ordinary chat, a loaded plan, or a client's presence. An unsupported peer gets `unsupported_capability` before admission. Private invocations, Pi compatibility, and legacy hosts do not gain this capability.

## Explicit launch and read-only inspection

All three operations take a native `threadId` string naming the original parent, not the worker thread. Requests and replies are JSON objects. Unknown fields and invalid bounds are rejected.

- `ext.delegation.start` takes `{threadId, requestId, scope, assignments, mode?, selection?, prompt?, workerTimeoutMs?}`. `scope` has `tracked` and `untracked` arrays of distinct exact paths relative to the parent's backend working directory (1–16 total). `assignments` has one or two ordered `{name, brief}` pairs (distinct names of up to 64 UTF-8 bytes; briefs up to 2048 bytes). The host snapshots base, index, and working versions of the named files. It rejects intent-to-add index entries rather than recording them as staged empty blobs. It never grants workspace trust. `mode` is `sequential` by default or explicitly `parallel`. Parallel permits overlap within that cohort only. An earlier unsettled reservation fences a later cohort. At most two assignments, including held and unresolved reservations, may be unsettled for one parent. There are at most 64 retained cohort receipts per parent; the host does not evict a recorded key to make room.
- Optional `selection` is `{model:{provider,modelId},thinking}` for **the reviewers**, otherwise the parent's current selection is pinned. Hush validates availability and the exact thinking level. It does not substitute a provider, model, or thinking level. `workerTimeoutMs` is 100–180000, default 120000, measured from admission of that worker's child submission, not the queue time.
- With no `prompt`, launch starts the workers but never starts a parent turn. `prompt` is one explicit native parent input (up to 2048 UTF-8 bytes, not a plan or skill request). It reserves the same assignments but starts them only if that exact turn calls `hush_spawn_reviews`. A held launch expires after two minutes; separate queued input, a Continue, and a fork cannot use it. A run with `prompt` uses the parent's normal workspace and model selection; the reviewers do not receive that prompt, the parent's history, or its draft. Start requires an idle parent. An exact retry can recover a receipt even while the parent is busy or its original workspace/model is unavailable. Same key with different normalized payload returns `invalid_request`. New requests over capacity return `limit`.
- `start` returns `{threadId, requestId, snapshotId, base, mode, selection, workers:[{handle,name}], submissionId?}` when reservation commits. `handle` is a 32-character lowercase hexadecimal assignment ID; `snapshotId` is a SHA-256 hex string. The optional `submissionId` is the ordinary parent input receipt, not a worker or outcome ID.
- `ext.delegation.get` takes `{threadId,requestId}`. It returns `{receipt,workers,target}`. `target` is `current`, `stale`, or `unavailable` relative to the captured scope. It does not alter the pinned bytes or an outcome. The workers are ordered as admitted. Each has `{handle,name,state,report?,detail?,noticeId?}`. States are `reserved`, `running`, `stopping`, `succeeded`, `failed`, `cancelled`, `timed_out`, and `unresolved`. Only a correlated committed terminal result has a `noticeId`. A `succeeded` result includes a bounded advisory `report`; a terminal failure, stop, timeout, or unresolved result includes `detail`. Reading any result does not approve work or advance plan progress.
- `ext.delegation.stop` takes `{threadId,handle}` and returns `{worker}` in the same shape. It addresses just that assignment. `stopping` is not settlement; capacity is freed only after a confirmed terminal outcome. A late Stop does not rewrite a committed result. Unknown handles and conflicting parents fail. Missing or contradictory storage evidence remains unresolved; no new task or child is reconstructed on its behalf.

## Acceptance checks and labeled evidence (`reviewEvidence:1`)

Offer `reviewEvidence: [1]` with `delegation: [1]`. When negotiated, `start` accepts optional `assessment: {checks?, evidence?}`. `checks` holds at most six `{id, description}` pairs (160 UTF-8 bytes per description); `evidence` holds at most four `{id, label, text}` excerpts (80 and 640 bytes respectively). IDs are unique within each array and match `[a-z][a-z0-9_-]{0,31}`. Supplied excerpts are data, not commands, executable tests, parent history, or proof a check passed. They and the checks are pinned at admission; a changed excerpt or check conflicts with an exact retry. Old hosts still accept launches without `assessment`; an assessment must not be silently dropped.

A fresh reviewer sees its brief, snapshot ID, and the pinned checks and excerpts. The structured form of `hush_review_report` records a summary, up to six prioritized findings (`P0`–`P3`, path, `base`/`staged`/`working` version, line, and message), an assessment per check, and at least one limitation. Citations to files and lines are checked against successful pinned reads in the worker's own submission. `inspected` refers to a source read, not an executed test. `supplied` must cite an admitted excerpt; it is labeled not rerun. `unverified` claims neither; omitted checks are also displayed as unverified. The backend renders and bounds the advisory report with the worker handle, pinned selection, observed report-call model/thinking if available, base, and snapshot ID. Old assignments without an assessment can still return the original bounded text report. A report cannot verify, approve, or authorize work. A stale or unavailable freshness check leaves the original report intact.

## Worker activity (`workerActivity:1`)

Offer `workerActivity: [1]` with `delegation: [1]`. Without it, clients still see committed notices if they negotiate `delegation:1`, but there is no roster or worker transcript API.

- `ext.workerActivity.wait` takes `{threadId,after?}` and returns `{threadId,cursor,workers}`. Rows are in admission order and include `{handle,name,state,activity}`. Read activity is committed, public and bounded; no reasoning, tool inputs or file bytes are published. The 64-character opaque cursor is scoped to this parent and host boot. A missing or different cursor returns a full baseline. An equal cursor waits for a changed observation or disconnect. Intermediate updates can be coalesced. Loss of a correlated worker's assigned policy can wake the roster with an unresolved row, even if the worker task does not change. Reattach without a cursor on transport loss; do not replay roster rows as notifications.
  If a worker task remains but its receipt is missing, the roster shows its original handle as `unresolved` with a placeholder name. It cannot supply a dossier or transcript, and it never frees capacity or reconstructs work.
- `ext.workerActivity.inspect` takes `{threadId,handle,transcript?}`. It returns the existing receipt and worker outcome, brief, scoped paths, any pinned assessment, and freshness observed for this inspection. `transcript: true` explicitly adds the bounded tail of public reviewer text and snapshot-read activity in entry order, without a child thread ID, raw tool output or private reasoning. Unresolved ownership fails closed for transcript access. Held workers may have no transcript yet. Foreign parents and ordinary native child history cannot be used in place of this API. Neither call submits input, changes a plan, grants trust, stops a worker, or opens a pane.

TUI attachment is silent. The roster uses replacement snapshots and the native parent feed retains ordered, deduplicated notice IDs, including after reconnect or window gaps. The TUI's worker count and `ctrl+x i j` open the same dock. Inspect before opening the read-only transcript. In a Rex block with the CLI available, `o` in the transcript explicitly opens a read-only snapshot in a right pane (`hush review transcript`); the pane is not used for execution, joining, or settlement. OS and thread-dashboard notifications are unchanged.

## Model spawn, join, and notices

The backend checks the original placed parent submission and task ownership at execution. `hush_spawn_reviews` takes no arguments: it releases exactly the user-approved reservation and returns its snapshot ID and named handles. If any held assignment cannot be correlated, spawn releases none of them. A correlated Stop outcome is never relaunched. `hush_join_reviews({handles,timeoutMs?})` is available to the same explicitly admitted parent turn, accepts one or two distinct released handles from that parent, and waits in that turn. A terminal notice for an unreleased handle can be inspected but does not make the handle joinable.

Join returns `{wait,outcomes}`. Outcomes are in input order and include each handle's state, snapshot ID, and committed report or diagnostic where available. `wait: "settled"` means every handle has a correlated terminal outcome. Join does not wait on unresolved evidence, but it still waits for any correlatable pending siblings. `wait: "timed_out"` means the join deadline elapsed with at least one such sibling still pending. If none remains pending and any handle's evidence is unresolved, `wait` is `"unresolved"`; the corresponding reservation still holds capacity. Join never cancels workers. A worker's terminal `state: "timed_out"` is separate. Late and repeated joins read receipts, not the worker's transcript. They do not refresh snapshot freshness; the results apply to the sealed target.

A worker's committed outcome has one `hush.worker.notice` entry on the parent. The entry is display-only in Durable. On a negotiated parent `subscribe` or `history`, the existing v1 entry envelope includes its attributed advisory text. It is not a user message, doesn't create a parent submission, and isn't inherited from another thread. Core history/state filtering keeps it and its anchors out of unnegotiated peers. Ordinary tool/assistant entries in the parent remain ordinary v1 entries, including results used by an actual model join. Worker transcripts are task-owned and not exposed through the normal thread picker or core thread reads, even when the assigned policy cannot be recovered. The parent feed uses the normal epoch, window, recovery and overflow logic; applications must deduplicate committed entries by ID, not interpret a retained notice as a fresh event on attachment.

Durable owns scheduling and execution. An interrupted worker is not replayed on restart. A restart correlates any already settled child submission and committed advisory report, or records failure after owned work drains. Unknown evidence holds capacity. Notices and join signals are committed with the worker outcome so a retry cannot publish twice. This is not a review gate, a test runner, or permission to merge. See the [backend contract](../../docs/delegation-contract.md) for boundaries and fixtures.
