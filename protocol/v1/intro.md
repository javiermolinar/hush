# Hush intro capability

Offer `{"intro":[2,1]}` in `hello.params.capabilities`. A persistent reference backend selects the highest offered version it supports. Version 1 remains a read-only report; version 2 adds scoped thread metadata and explicit actions. Bare servers and invocation-private hosts do not advertise it. This extension is independent of `piEvents` and uses the [intro schema](intro.schema.json); it does not change the core schema.

`ext.intro.get` takes `{threadId?, cwd?, after?}`. `threadId` selects an existing conversation. Without a thread, `cwd` can select an existing absolute local workspace for a prospective conversation. The host applies Pi trust and does not start tools or create a conversation to preview it. Omit both to inspect the backend's main conversation. A nonexistent explicit scope returns `not_found`. Omit `after` for an immediate full report. Pass the last report's revision to wait for a higher revision. Send at most one pending report request per connection, and close the connection to cancel a passive wait. A revision belongs to the backend epoch and is an invalidation watermark, not a history cursor. Reconnect without `after`. Reports are replacement views and may coalesce changes; they do not prove run settlement.

The report contains the runtime start time (`startedAtMs`, zero if unknown), workspace, resolved model if present, thinking level, session counts, up to three attention items plus an overflow count, loaded skill names, and context sizing when the model window is known. Session counts cover ownerless Durable conversations; background work and task-owned child conversations are not counted as independent sessions. The reference backend samples at most 256 recent conversation records and marks the result `partial` if fewer than all records were scanned. Skill names are limited to 512 with an overflow count. A blank skills list is a known empty list.

The backend uses one shared Durable task graph and snapshots `pi.live` for failed runs. Skill names come from the same trust-aware project loader as the agent. Context sizing counts UTF-8 bytes in its rendered system sections and model-facing tool declarations. If an explicitly selected thread's latest committed entry is a successful same-model response with usage and no head/edit change on that entry, the report includes that response's context token count. It is not cumulative usage or a prediction of the next request. Reading the report does not create a conversation, open a Pi writer lease, or start a model request.

## Version 2

An explicit thread scope returns `thread: {id, title?, issue?, dismissedFailureId?}`. Attention rows include `threadId` and stopped rows include an `issue` instead of a reason string. An issue contains the settled task ID, the Durable reason, optional `detail` and `endedAtMs`, and booleans `retry` and `switchModel`. Those flags describe available native recovery; model selection still depends on the client having a catalog. Aborted, reset, and nothing-to-answer outcomes are not issues. A dismissal hides that task from the inventory and is reflected on the scoped thread while the same failure remains current.

The title comes from Hush's presentation document: explicit Hush title, then saved Pi name, then a bounded first-message excerpt. Only that excerpt, not the full prompt or expanded skill body, is used for the automatic title. Recognizable causes from `pi.live.runFailure.detail` are projected as bounded diagnostics. Unknown causes fall back to the category; the report never forwards raw provider payloads, headers, tool schemas or skill bodies.

- `ext.intro.rename {threadId, title}` stores a nonempty presentation title for an ownerless thread and returns its normalized `{title}`. It does not rename a Pi session.
- `ext.intro.retry {threadId, taskId}` admits a native Continue and returns `{submissionId}`. It does not claim settlement. The host verifies the exact failure, thread is idle, usable model, and native write ownership. Do not automatically retry an indeterminate transport error.
- `ext.intro.dismiss {threadId, taskId}` records a dismissal of that exact issue and returns `{}`. It does not modify the run, its task, or any submission settlement.

Retry and dismissal reject stale or mismatched task IDs and cannot affect a newer run. A v1 peer gets the v1 report shape and cannot call these actions.

Listing is read-only. An explicit `/skill:<name> [arguments]` goes through ordinary native `submit`; the reference backend looks up the name again against current project trust, expands the loaded skill, and rejects an unavailable name before admission. Picking a skill in the TUI only stages this text for review.
